# AGENTS.md

Конвенции разработки для хакатона InnoGlobalHack × Avito.
Задача кейса: по тексту объявления (`description`) и его текущей микрокатегории
(`mcId`) найти услуги, которые исполнитель предлагает в других микрокатегориях
категории «Ремонт и отделка», и сформировать дополнительные черновики объявлений.

**Контракт входа/выхода зафиксирован условиями кейса и меняется только с
согласования всей команды.**

Вход:

```json
{ "description": "текст объявления", "mcId": 101 }
```

Выход:

```json
{ "drafts": [{ "mcId": 104, "title": "...", "text": "..." }] }
```

Микрокатегории (не создаём новых, не выходим за таблицу):

| mcId | Микрокатегория                    |
| ---- | --------------------------------- |
| 101  | Ремонт под ключ                   |
| 102  | Штукатурные работы                |
| 103  | Плиточные работы                  |
| 104  | Сантехника                        |
| 105  | Электрика                         |
| 106  | Поклейка обоев и малярные работы  |

## 1. Структура репозитория

```
.
├── main.py                      # CLI-ядро + всё общее: контракт, микрокатегории,
│                                #   BasePipeline, LLMClient
├── subcategory_extraction/      # шаг 1: jev-модель выделяет подкатегории услуг
│   ├── pipeline.py              #   класс пайплайна
│   ├── prompts/                 #   промпты вынесены из кода
│   ├── benchmarks/              #   бенчмарки (.md, по файлу на бенчмарк)
│   ├── tests/                   #   только бенчмарк-прогоны
│   └── README.md
├── category_validation/         # шаг 2: проверка выбранных категорий
├── draft_generation/            # шаг 3: генерация черновиков объявлений
├── backlog/                     # локальный бэклог каждого (в .gitignore)
│   └── <username>/{TODO,PROCESS,REVIEW,DONE}
├── data/                        # примеры входных данных
├── docs/                        # кейс, критерии, справочник микрокатегорий, датасеты
├── requirements.txt             # зависимости (ставим через uv)
├── pytest.ini                   # конфиг тестов
├── .env.example                 # шаблон переменных окружения (.env в git не коммитим)
└── AGENTS.md
```

Правила:

- **Один сервис — одна папка.** Внутри папки сервиса обязательно есть
  `benchmarks/`.
- `main.py` **импортирует классы пайплайнов** и только оркеструрует вызовы.
  Бизнес-логика живёт в пайплайнах, не в `main.py`.
- Всё общее (таблица микрокатегорий, схемы контракта, `BasePipeline`,
  `LLMClient`) — в `main.py`, не дублировать по сервисам. Сервисы импортируют
  общее из `main`; импорты сервисов в `main.py` делаются внутри
  `run_pipeline()`, иначе циклическая зависимость.
- Переменные окружения — в `.env` (шаблон `.env.example`), `main.py` подгружает
  их через `load_dotenv()`. Секреты в репозиторий не коммитим.

## 2. Пайплайн

1. **Выделение подкатегорий.** jev-модель по тексту объявления определяет
   микрокатегории (101–106), к которым относятся описанные услуги.
2. **Проверка выбранных категорий.** Оставляем только категории из таблицы,
   исключаем исходную `mcId`, дедуплицируем, отбрасываем мусорные ответы модели.
3. **Генерация черновиков.** Под каждую валидную категорию — отдельный
   черновик. Текст пишется только по фактам из исходного объявления: ничего
   не додумываем, не ссылаемся на исходное объявление, не утверждаем, что
   услугу можно заказать отдельно, если это не следует из текста.

---

## 3. main.py — ядро проекта

```bash
python main.py --input data/input.json --output out/output.json
```

- Принимает путь к файлу ввода и генерирует файл вывода через флаги
  `--input` / `--output`.
- Импортирует классы каждого из пайплайнов и собирает их в цепочку.
- Содержит всё общее для сервисов: таблицу микрокатегорий, схемы контракта
  (`PipelineInput` / `Draft` / `PipelineOutput`), `BasePipeline`, `LLMClient`.
- В начале `main()` подгружает переменные из `.env` (`load_dotenv()`):
  `LLM_MODEL_ID`, `LLM_API_KEY`.
- Без побочных эффектов на импорте: `if __name__ == "__main__":`.
- Логика «прочитать JSON → прогнать пайплайн → записать JSON» — только здесь.

## 4. Бенчмарки

- Папка: `<service>/benchmarks/`.
- **Каждый бенчмарк — новый `.md` файл.** Имя: `YYYY-MM-DD_<slug>.md`.
- Входные данные бенчмарка лежат в `.md` в блоке ```json. Единственный тест
  сервиса (`tests/test_benchmark.py`) прогоняет пайплайн на этих данных и
  проверяет контракт; запуск — `uv run pytest`.
- Данные для бенчмарков — из `docs/innoglobalhack_avito/`:
  `public-train-annotated.jsonl` (10 000 размеченных объявлений) и
  `public-test-dataset.parquet` (208 записей).
- **Каждое обновление кода → перезапуск бенчмарков → обновление `.md`** с
  результатами. Устаревшие результаты не оставляем.
- **Каждый новый бенчмарк перед коммитом прогоняется на всех версиях кода**:
  заполняется таблица по версиям (commit / дата / метрики), чтобы сразу было
  видно регрессии.

Шаблон `benchmarks/YYYY-MM-DD_<slug>.md`:

```markdown
# Бенчмарк: <что проверяем>
Сервис: <service>
Дата: YYYY-MM-DD   Автор: <username>

## Что проверяем и почему
<цель, данные, метрики: accuracy / macro-F1 по mcId, доля валидного JSON,
   доля галлюцинаций, доля черновиков ≠ исходной mcId и т.п.>

## Результаты по версиям
| commit | дата | метрика 1 | метрика 2 | ... |
| ------ | ---- | --------- | --------- | --- |

## Выводы
<что улучшилось / сломалось, что делать дальше>
```

## 5. Бэклог и ветки

- У каждого участника свой **локальный** бэклог: `backlog/<username>/{TODO,PROCESS,REVIEW,DONE}`.
  Папка `backlog/` в `.gitignore` — в репозиторий не коммитится, у каждого своя.
- Задача — `.md` файл: заголовок, описание, критерий готовности, ссылка на ветку.
- **Каждая фича — новая ветка.** Имя ветки: `<username>/feature/<короткий-slug>`
  (для фиксов: `<username>/fix/<slug>`).
- **В начале каждого чата перепроверяй, в какой ветке ты находишься**
  (`git branch --show-current`) и в какой папке бэклога лежит активная задача.
- Поток задачи: `TODO` → создали ветку, задача в `PROCESS` → открыли PR, задача
  в `REVIEW` → после мержа задача в `DONE`.
- В `main` не коммитим. Только через PR.

## 6. Чистота кода

- Python 3.11+, типизация (type hints) везде, где возможно. Докстринги — на русском.
- Именование: модули и функции — `snake_case`, классы — `PascalCase`,
  константы — `UPPER_CASE`.
- Один пайплайн — один класс с методом `run(...)`. Класс не делает ничего при
  импорте.
- Не хардкодим: id и названия микрокатегорий, пути, параметры модели — в
  константы/конфиг/`.env`. Секреты и ключи — только вне репозитория.
- `print` не используем — только `logging`.
- Исключения не глотаем молча; ошибки валидации выхода LLM обрабатываем явно.
- Ответ LLM валидируем (pydantic / проверка схемы), не доверяем строке на честном слове.
- Функции небольшие и с одной ответственностью. Мёртвый и закомментированный код
  удаляем — историю хранит git.
- Дублирование выносим в `main.py` (общий код для всех сервисов).

## 7. Отношение к правкам напарников

- **Чужой код не переписываем молча.** Любая правка в чужом сервисе — через
  задачу в своём бэклоге и собственную ветку; в описании PR пишем, что и почему
  меняем.
- **Публичный контракт** (формат ввода/вывода `main.py`, формат `drafts`) меняется
  только после согласования со всеми, кто на него опирается.
- **Сначала разговор, потом правка.** Если видишь баг или спорное решение в чужом
  коде — создай задачу в `TODO` и скажи автору, а не правь «по ходу».
- Задача из `REVIEW` мержится только с апрувом хотя бы одного напарника.
  Комментарии на ревью — по делу, с предложением альтернативы.
- Не тащим в свою ветку чужые незакоммиченные изменения и не форсим пуш в `main`.

## 8. Definition of Done (перед коммитом / мержем)

- [ ] Ветка создана по соглашению из этого файла.
- [ ] Тесты проходят (`pytest`).
- [ ] Новый бенчмарк прогнан на всех версиях кода, `.md` обновлён.
- [ ] `python main.py --input <файл> --output <файл>` работает на актуальных данных.
- [ ] Задача лежит в правильной папке бэклога (`PROCESS` → `REVIEW` после PR).
- [ ] Правки в чужих сервисах согласованы с автором.
