# AGENTS.md

Конвенции разработки для хакатона InnoGlobalHack × Avito.
Задача кейса: по тексту объявления (`description`) и его текущей микрокатегории
(`mcId`) найти услуги, которые исполнитель предлагает в других микрокатегориях
категории «Ремонт и отделка», и сформировать дополнительные черновики объявлений.

**Контракт входа/выхода зафиксирован условиями кейса и меняется только с
согласования всей команды.**

Вход:

```json
{ "description": "текст объявления", "mcId": 101 }
```

Выход:

```json
{ "drafts": [{ "mcId": 104, "title": "...", "text": "..." }] }
```

Микрокатегории (не создаём новых, не выходим за таблицу):

| mcId | Микрокатегория                    |
| ---- | --------------------------------- |
| 101  | Ремонт под ключ                   |
| 102  | Штукатурные работы                |
| 103  | Плиточные работы                  |
| 104  | Сантехника                        |
| 105  | Электрика                         |
| 106  | Поклейка обоев и малярные работы  |

## 1. Структура репозитория

```
.
├── src/                         # весь исполняемый код
│   ├── main.py                  # CLI-ядро + всё общее: контракт, микрокатегории,
│   │                            #   BasePipeline, LLMClient
│   ├── subcategory_extraction/  # шаг 1: выделение подкатегорий услуг
│   │   ├── jev/                 #   пример будущего варианта (когда реализован)
│   │   │   ├── __init__.py
│   │   │   ├── pipeline.py      #   SubcategoryExtractionPipeline
│   │   │   └── prompts/         #   промпты этого варианта
│   │   ├── embeddings/          #   пример будущего варианта (когда реализован)
│   │   ├── llm/                 #   пример будущего варианта (когда реализован)
│   │   ├── benchmarks/          #   общие бенчмарки раздела
│   │   │   └── <name>/
│   │   │       ├── run.py     #   точка входа бенчмарка
│   │   │       └── README.md  #   описание и таблицы прогонов
│   │   └── README.md
│   └── draft_generation/        # шаг 2: варианты + общие benchmarks/
├── config.json                  # выбранный модуль для каждого раздела
├── backlog/                     # локальный бэклог каждого (в .gitignore)
│   └── {TODO,PROCESS,REVIEW,DONE}
├── data/                        # примеры входных данных
├── docs/                        # кейс, критерии, справочник микрокатегорий, датасеты
├── pyproject.toml               # зависимости (ставим через uv sync)
├── .python-version              # версия Python для uv
├── .env.example                 # шаблон переменных окружения (.env в git не коммитим)
└── AGENTS.md
```

Правила:

- Весь исполняемый код — в `src/`; ниже `main.py` означает `src/main.py`.
- **Один раздел (сервис) — одна папка, один вариант — вложенная папка.**
  Внутри раздела обязательно есть общие `benchmarks/`, а реализации
  лежат в `<module>/pipeline.py`; промпты и ресурсы — внутри своего модуля.
  Варианты (`embeddings`, `llm`, `jev` и другие) решают одну задачу и сохраняют
  одинаковый интерфейс раздела. Пустые папки под ещё не написанные варианты не создаём.
- **Все новые экспериментальные решения оформляем как новые модули
  существующих разделов:** `src/<service>/<module>/pipeline.py`, с тем же
  интерфейсом и выбором через `config.json`. Отдельную папку `experiments/`
  не создаём. Промпты и ресурсы храним внутри модуля, скрипты сравнения,
  входные выборки и результаты — в `src/<service>/benchmarks/<name>/`.
  Исторические результаты не выдаём за оценку новой реализации.
- `main.py` загружает выбранные в `config.json` классы и только оркестрирует
  вызовы. Бизнес-логика живёт в модулях, не в `main.py`.
- Всё общее (таблица микрокатегорий, схемы контракта, `BasePipeline`,
  `LLMClient`) — в `main.py`, не дублировать по сервисам. Сервисы импортируют
  общее из `main`; импорты сервисов в `main.py` делаются внутри
  `load_pipeline()` во время вызова, иначе циклическая зависимость.
- Переменные окружения — в `.env` (шаблон `.env.example`), `main.py` подгружает
  их через `load_dotenv()`. Секреты в репозиторий не коммитим.

## 2. Пайплайн

1. **Выделение подкатегорий.** Выбранный модуль по тексту объявления определяет
   микрокатегории (101–106), к которым относятся описанные услуги.
2. **Генерация черновиков.** Полученные идентификаторы передаём напрямую
   в модуль генерации. Под каждую целевую категорию — отдельный
   черновик. Текст пишется только по фактам из исходного объявления: ничего
   не додумываем, не ссылаемся на исходное объявление, не утверждаем, что
   услугу можно заказать отдельно, если это не следует из текста.

## 3. main.py — ядро проекта

```bash
python src/main.py --input data/input.json --output out/output.json
```

- Принимает путь к файлу ввода и генерирует файл вывода через флаги
  `--input` / `--output`.
- Читает корневой `config.json`, проверяет его через `PipelineConfig`,
  загружает выбранные классы через `load_pipeline()` и собирает их в цепочку.
  Путь к конфигу определяется относительно `main.py`, а не текущего каталога.
- Содержит всё общее для сервисов: таблицу микрокатегорий, схемы контракта
  (`PipelineInput` / `Draft` / `PipelineOutput`), `BasePipeline`, `LLMClient`.
- В начале `main()` подгружает переменные из `.env` (`load_dotenv()`):
  `LLM_MODEL_ID`, `LLM_API_KEY`.
- Без побочных эффектов на импорте: `if __name__ == "__main__":`.
- Логика «прочитать JSON → прогнать пайплайн → записать JSON» — только здесь.

### Выбор и добавление модулей

```json
{
  "subcategory_extraction": null,
  "draft_generation": null
}
```

Оба ключа обязательны; значение — имя папки модуля в соответствующем
разделе, а не идентификатор LLM. `null` означает, что реализация пока не выбрана:
CLI завершается явной ошибкой.
Доступны `subcategory_extraction/google_decision` и `draft_generation/llm`.
Генератор поддерживает Google Gemma и OpenAI-compatible API через `.env`.
После выбора рабочего модуля заменяем `null` его именем.
Неизвестные ключи, некорректные имена и
отсутствующие модули — ошибка, без молчаливого переключения на другой вариант.
Параметры модели и секреты по-прежнему задаются через `.env`.

Новый вариант добавляем в `src/<service>/<module>/` с `__init__.py` и
`pipeline.py`. Класс наследует `BasePipeline`, создаётся без обязательных
аргументов и сохраняет имя и сигнатуру своего раздела:

| Раздел | Класс | Метод |
| --- | --- | --- |
| `subcategory_extraction` | `SubcategoryExtractionPipeline` | `run(inp: PipelineInput) -> list[int]` |
| `draft_generation` | `DraftGenerationPipeline` | `run(inp: PipelineInput, target_mc_ids: list[int]) -> list[dict]` |

Для переключения достаточно изменить `config.json`; код оркестрации менять
не нужно. Сравниваем варианты на общих бенчмарках раздела и выбираем лучший.
Программно можно передать `PipelineConfig` в `load_pipeline()` / `run_pipeline()`.

## 4. Бенчмарки

- Каждый бенчмарк — отдельная папка `src/<service>/benchmarks/<name>/`:
  - `run.py` — точка входа для прогона;
  - `README.md` — цель, данные, метрики, команды запуска и таблицы прогонов.
- Имя папки — понятное название без даты, в `snake_case`. Даты — в таблицах.
  Вспомогательные скрипты, выборки и сохранённые ответы лежат рядом.
  Общие метрики нескольких бенчмарков могут оставаться в `benchmarks/metrics.py`;
  общие замеры, выборки и запись отчётов — в `src/benchmark_support.py`.
- Бенчмарки общие для всех модулей раздела. При смене модуля не меняем
  чтение данных, расчёт метрик и проверки контракта.
- `run.py` запускается из корня: `uv run python src/<service>/benchmarks/<name>/run.py`.
  Разные сценарии описываем в README с точными командами и параметрами.
  Маленькие контрольные входы можно хранить в README в JSON-блоке;
  для датасетов указываем путь, версию/хеш и способ формирования выборки.
- В общей сравнительной таблице указываем сценарий, версию кода, дату,
  модуль/модель, лучший системный промпт, метрики качества, время и стоимость.
  Для решений без промпта
  ставим `—`. Сценарии с разными данными или обработкой ответов не смешиваем.
- Если решение использует системный промпт, добавляем отдельную таблицу
  «промпт — результат» для всех проверенных вариантов на одном сценарии.
  Указываем файл/версию промпта; если исходный текст не сохранился, говорим об этом.
  Лучший промпт выбираем по заранее указанной метрике на validation;
  лучший сохранённый результат на другой выборке помечаем как исторический,
  а не как основание для изменения рабочего промпта.
- Исторические результаты сохраняем с исходными датами и версиями.
  Офлайн-пересчёт сохранённых ответов не выдаём за новый вызов модели.
  Сборные архивы вроде `historical/` в `benchmarks/` не создаём: каждый
  рабочий сценарий имеет понятную папку с run.py и README.md.
  Невоспроизводимые старые эксперименты не выдаём за рабочие бенчмарки;
  удалённый код и прежние результаты доступны в истории Git.
- Время ответа измеряем через `perf_counter()` вокруг настоящего вызова
  `run()`. Указываем число вызовов, среднее, медиану и p95 в секундах.
  Записываем, входят ли загрузка модели, ожидание квоты и повторы запросов.
  Время офлайн-проверки или пересчёта кэша не называем временем ответа модели.
- Стоимость заполняет вручную человек или агент в README по факту тарифа/квоты.
  Для локальных и бесплатных прогонов пишем **«бесплатно»**. Для платных —
  сумму, валюту и объём прогона; неизвестную цену не придумываем.
  Отдельный скрипт стоимости и автоматический расчёт цены не нужны.
- Отчёт каждого нового прогона сохраняем рядом как `results.json` (или
  `<scenario>-results.json`), с датой, commit/отпечатком кода и результатами.
  Неполный прогон помечаем как неуспешный без итогового F1; не заменяем его
  последней успешной метрикой. После прогона перезаписываем актуальные
  таблицы README фактическими значениями, включая время и ручную стоимость.
- Аудит, переразметка и сборка датасета хранятся отдельно от бенчмарков
  моделей; код переработки данных не размещаем в `benchmarks/`.
- Тестов и тестового фреймворка в проекте нет: используем бенчмарки;
  не добавляем `tests/`, `test_*.py` и зависимость `pytest`.
- **Обучение, подбор параметров и оценка новых моделей — только на данных
  InnoGlobalHack.** В `docs/innoglobalhack_avito/`:
  - `public-train-annotated.jsonl` — 10 000 объявлений с автоматической
    разметкой `found_microcategories`; исходная категория всегда 101.
    Используем для обучения и внутренних validation/test-разбиений.
    Дубликаты и близкие варианты одного описания держим в одной части.
  - `public-test-dataset.parquet` — отдельные 208 записей с названиями
    категорий. Используем для итоговой оценки после фиксации модели,
    промпта и порогов. Проверяем пересечение с обучающими текстами и
    соответствие названий категорий целевому контракту до расчёта F1.
  - Purple Hack и объединённый `local-notes/joined-datasets/train.csv`
    остаются источниками исторических результатов. Purple Hack размечает
    самостоятельно заказываемые услуги, а InnoGlobalHack — услуги, которые
    исполнитель предлагает, включая явно предложенные этапы ремонта.
    Это разные целевые метки для обучения и оценки.
- **При обновлении кода перезапускаем затронутые сценарии** и добавляем
  результаты в README. Историю не стираем; старые цифры не называем актуальными.
- **Перед коммитом нового бенчмарка прогоняем его на всех версиях кода**
  и заполняем таблицу. Отсутствующий модуль или недоступные данные явно отмечаем;
  не подставляем результаты другой реализации.

Шаблон `src/<service>/benchmarks/<name>/README.md`:

```markdown
# Бенчмарк: <название>
Сервис: <service>

## Что проверяем
<цель, данные/хеш, выборка, метрики, правило выбора лучшего промпта>

## Запуск
<команды run.py для каждого сценария; API или офлайн; куда сохраняется отчёт>

## Сравнение решений
| Сценарий | Версия / дата | Модуль / модель | Лучший промпт | Качество | N | Среднее / медиана / p95, с | Стоимость |
| --- | --- | --- | --- | --- | --- | --- | --- |

## Промпты
| Сценарий | Модуль / модель | Промпт (файл / версия) | Версия кода / дата | Качество | N | Среднее / p95, с | Стоимость |
| --- | --- | --- | --- | --- | --- | --- | --- |

## Выводы
<что подтверждено, ограничения и следующий шаг>
```

Таблица промптов нужна только решениям, которые используют промпты.

## 5. Бэклог и ветки

- У каждого участника свой **локальный** бэклог: `backlog/{TODO,PROCESS,REVIEW,DONE}`.
  Папка `backlog/` в `.gitignore` — в репозиторий не коммитится, у каждого своя.
- Задача — `.md` файл: заголовок, описание, критерий готовности, ссылка на ветку.
- **Каждая фича — новая ветка.** Имя ветки: `<username>/feature/<короткий-slug>`
  (для фиксов: `<username>/fix/<slug>`).
- **В начале каждого чата перепроверяй, в какой ветке ты находишься**
  (`git branch --show-current`) и в какой папке бэклога лежит активная задача.
- **Перед началом работы синхронизируй ветку с удалённым репозиторием:**
  проверь `git status`, выполни `git fetch origin`, затем `git pull --ff-only`.
  Если есть незакоммиченные изменения, сначала безопасно сохрани их и после
  обновления восстанови; при конфликтах или расхождении веток не делай reset
  и не перезаписывай чужую работу. Не считай локальную ветку актуальной без fetch.
- Поток задачи: `TODO` → создали ветку, задача в `PROCESS` → открыли PR, задача
  в `REVIEW` → после мержа задача в `DONE`.
- В `main` не коммитим. Только через PR.

## 6. Чистота кода

- Python 3.11+, типизация (type hints) везде, где возможно. Докстринги — на русском.
- Именование: модули и функции — `snake_case`, классы — `PascalCase`,
  константы — `UPPER_CASE`.
- Один вариант пайплайна — один класс с методом `run(...)`. Все варианты
  раздела соблюдают одинаковый интерфейс. Класс не делает ничего при импорте.
- Не хардкодим: id и названия микрокатегорий, пути, параметры модели — в
  константы/конфиг/`.env`. Секреты и ключи — только вне репозитория.
- `print` не используем — только `logging`.
- Исключения не глотаем молча; ошибки валидации выхода LLM обрабатываем явно.
- Ответ LLM валидируем (pydantic / проверка схемы), не доверяем строке на честном слове.
- Функции небольшие и с одной ответственностью. Мёртвый и закомментированный код
  удаляем — историю хранит git.
- Дублирование выносим в `main.py` (общий код для всех сервисов).

## 7. Отношение к правкам напарников

- **Чужой код не переписываем молча.** Любая правка в чужом сервисе — через
  задачу в своём бэклоге и собственную ветку; в описании PR пишем, что и почему
  меняем.
- **Публичный контракт** (формат ввода/вывода `main.py`, формат `drafts`) меняется
  только после согласования со всеми, кто на него опирается.
- **Сначала разговор, потом правка.** Если видишь баг или спорное решение в чужом
  коде — создай задачу в `TODO` и скажи автору, а не правь «по ходу».
- Задача из `REVIEW` мержится только с апрувом хотя бы одного напарника.
  Комментарии на ревью — по делу, с предложением альтернативы.
- Не тащим в свою ветку чужые незакоммиченные изменения и не форсим пуш в `main`.

- [ ] Ветка создана по соглашению из этого файла.
- [ ] Если есть рабочие реализации и бенчмарки — результаты обновлены.
- [ ] Новый бенчмарк прогнан на всех версиях кода, его `README.md` обновлён.
- [ ] `python src/main.py --input <файл> --output <файл>` работает на актуальных данных.
- [ ] Задача лежит в правильной папке бэклога (`PROCESS` → `REVIEW` после PR).
- [ ] Правки в чужих сервисах согласованы с автором.

## 10. Локальные инструкции

- В начале каждого чата проверяй, существует ли `local_agents.md` в корне
  репозитория, и всегда читай его, если он есть. Файл локальный и исключён
  из Git.
