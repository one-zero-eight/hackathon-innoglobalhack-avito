# Бенчмарк генерации: контракт, подтверждённость фактов и сохранение деталей
Сервис: draft_generation

## Что проверяем

Штатный `sample_llm`: JSON-схему, категории, дубликаты целей, пустые цели,
ошибки транспорта и повторы, полную цепочку через `run_pipeline`.
Ответы транспорта подменены контрольными фикстурами, настоящая LLM не вызывается.
Это проверка контракта, не оценка качества или достоверности текста.

```json
{"description":"Устанавливаю розетки и смесители.","mcId":101}
```

Цели:104/105; JSON-фикстура ответа:
`{"title":"Монтаж","text":"Установка смесителей."}`.

## Запуск

```bash
uv run python src/draft_generation/benchmarks/sample_llm/run.py
```

Выход: [results.json](results.json). Внешних запросов и расходов нет.

Судья по умолчанию — `StructuredLLMClient`, `STRUCTURED_LLM_MODEL` /
`STRUCTURED_LLM_ENDPOINT`, ключ `BESTAPI_API_KEY`, валидируемый кеш
`STRUCTURED_LLM_CACHE_DIR`. Альтернативный доступный Google-судья выбирается
**явно и одинаково** для references/evaluate:
`--judge-provider gemini --judge-model gemini-3.5-flash` (ключ `LLM_API_KEY`).
Это другая модель, чем штатный генератор, но same-family bias относительно Gemini
остается; provider/model и этот риск сохраняются в отчетах. У Google используется
responseJsonSchema, кеша API-ответов здесь нет, только resume артефактов.
Недоступность внешнего судьи не превращается в фиктивные оценки.
Для structured можно переопределить модель флагом `--judge-model`.
Ключи и query-параметры endpoint в метаданные не выводятся.

### Выборка и воспроизводимость

Только `docs/improved_dataset/train.jsonl`: описания группируются по NFKC,
casefold, `ё→е` и схлопыванию пробелов; конфликтующие группы исключаются.
Группы идут в порядке первого появления. Разбиение:
`train_test_split(test_size=.3, random_state=42)`, затем validation — первая
половина remaining при `test_size=.5, random_state=43`. Official test не читается.
Seed управляет перемешиванием validation; выбираются по 10 пар для целей 102–106
при size=50, и максимально разные источники. Для другого size остаток
распределяется по возрастанию целей; цель берется только из found_microcategories.
Несовпадающий существующий samples.json не перезаписывается.

`--limit 1` у generate/references/evaluate — маленький реальный smoke, не полный
бенчмарк: scope явно содержит limit/limited/missing/complete. Без limit берутся все
пары. Успехи возобновляются без повторных вызовов, ошибки повторяются только при
явном новом запуске этапа. Внутри запуска повторных запросов и переписываний
ответов нет (Gemini max_attempts принудительно 1).
Модель/endpoint/параметры/промпт и входы закреплены identity; несовместимые
артефакты требуют другого output-dir, а не молчаливого смешивания.
При явном повторном запуске предыдущие неудачные попытки и их usage остаются
в `previous_attempts`; успешные ответы не генерируются заново.

### Две метрики, без общего балла

* **Подтвержденность фактов:** supported / все атомарные утверждения title+text.
  Судья извлекает в том числе выдуманные услуги, цены и обещания. Для supported
  проверяется непустая точная цитата исходника, иначе evidence обязан быть пустым.
* **Сохранение полезных деталей цели:** covered / все факты frozen reference.
  Эталон извлекается без доступа к ответам кандидатов, только из исходника,
  с условиями/отрицаниями и точными цитатами. Детерминированные fact_id проверяются,
  а covered требует точной цитаты черновика. Интернет-обогащение запрещено.
  Принадлежность услуг задаётся официальным
  `docs/innoglobalhack_avito/microcategories-guide.md`, включённым в промпт
  оценщика. Справочник не добавляет услуг, отсутствующих в исходнике.
  В частности, шпаклёвка относится к 106, а не к 102.

Числители/знаменатели и ratios считает Python, не судья. Micro — отношение
сумм, macro — среднее определенных per-sample ratios с их количеством.
Пустой список утверждений или пустой эталон дает `null` соответствующей метрике,
а не 100%. Ошибка/отсутствие генерации или оценки дает две `null`, статус и счетчик;
неоцененные пары тоже показаны. Успешная оценка не означает ненулевой знаменатель.
Micro на неполном scope описывает только доступные успешно оцененные пары:
сравнивать ее с полным прогоном без учета scope нельзя.

### Артефакты и ограничения

* `samples.json`: описание, mcId=101, target_mc_id, id, item_id, source/group hashes,
  dataset_sha256, seed и точный sampling_protocol.
* `generation-<label>.json`: identity модели/endpoint/параметров и промпта, metadata,
  records по sample id: draft, raw_response (в том числе невалидный JSON),
  error, error_detail, status, latency_seconds, usage и scope.
  Local использует prompt JSON + Pydantic, **без constrained decoding**;
  Gemini — provider defaults + responseJsonSchema. Это различие записано.
* `references.json`: автоматические facts/evidence/fact_id, source_hash,
  raw_response, usage, cache_hit, prompt_sha256, judge и scope.
* `evaluation-<label>.json`: отдельные ответы слепого к label/model судьи,
  claims и covered_facts, проверенные счетчики, ratios, статусы, aggregate.
  При ошибках схемы/цитат сохраняется error_detail без входов Pydantic и URL.
* `comparison.json` и `comparison.md`: обе micro и macro, знаменатели,
  количество определенных оценок, ошибки/пропуски, scope, параметры судьи.
  Общие API usage проходят через track_llm_costs; тарифы не выдумываются.
  `common_cohort` отдельно считает обе метрики на одних и тех же парах,
  где у каждой сравниваемой модели определены обе оценки. Размер и категории
  пересечения сохраняются; неполное пересечение может быть смещено квотой API.

Это **автоматический эталон и автоматические оценки, не независимый ручной gold**.
Проверка подстрок подтверждает происхождение цитат, но не доказывает полноту
извлечения и семантическое следование: судья может ошибаться. Нет гарантии
побитовой воспроизводимости внешних моделей даже при одинаковых параметрах.
Фиксация артефактов и кеша позволяет пересмотреть реальные ответы без их подмены.
Таблица офлайн-контракта выше не является результатом оценки текстов.
Измеренный live-прогон описан ниже.

### Реальные ответы оценщика через модельный канал omp

Если API недоступен, реальные ответы `omp.eval.completion(model="default")`
можно сохранить и проверить без повторного модельного вызова:

```bash
uv run python src/draft_generation/benchmarks/sample_llm/compare.py --stage references --judge-provider recorded --judge-responses-dir out/draft-judge-cache --output-dir out/draft-model-comparison-v2
uv run python src/draft_generation/benchmarks/sample_llm/compare.py --stage evaluate --judge-provider recorded --judge-responses-dir out/draft-judge-cache --labels qwen35-4b qwen35-9b gemma3-12b gemini --output-dir out/draft-model-comparison-v2
```

Это **replay настоящих ответов**, не заглушка и не автоматическое переключение:
отсутствующий ответ даёт ошибку, а не оценку. Файл
`<digest(prompt)>.json` содержит `prompt_sha256`, `schema_sha256`, `response`,
`provenance.channel="omp.eval.completion"`, `provenance.model_alias="default"`
и настоящий `provenance.completion_id`. Ответ дополнительно проходит те же
Pydantic-проверки и проверки точных цитат.

Точный идентификатор модели и upstream usage этого канала не предоставляются;
они не выдумываются. Alias и идентификаторы вызовов сохранены. Время чтения
кеша не является временем модели; ноль новых API-вызовов при replay не означает
бесплатную исходную оценку. Эти оценки тоже не являются ручным gold.

Две выбранные метрики **не штрафуют правдивые, но нерелевантные услуги**:
копирование всего исходника может получить высокую оценку. Поэтому результаты
не являются оценкой готовности объявления к публикации или заменой оценки жюри.

## Измеренный первый прогон

Дата: 2026-11-14, базовый commit `185621a`, рабочее дерево.
Машина: Apple M4 Pro, 48 GiB. Оба Qwen — 4 bit, temperature 0.2,
seed 43, максимум 2048 выходных токенов, без thinking. Промпт одинаковый.
Ни обучения, ни официального test в этом сравнении нет.

Каждый Qwen создал **50/50 настоящих черновиков**. Восемь автоматических
эталонов не содержали релевантных фактов, поэтому полнота на них не определена.
На одном и том же дополнительном входе ответы оценщика для обоих Qwen
отклонены из-за неточных цитат; ошибка не заменена нулём или успехом.
Итоговое парное сравнение — **41 одинаковый вход**:

| Модель | Подтверждённость micro | Сохранение деталей micro | Подтверждённость macro | Сохранение деталей macro |
| --- | ---: | ---: | ---: | ---: |
| Qwen3.5-4B | 96.17% (929/966) | 55.52% (166/299) | 94.30% | 65.42% |
| Qwen3.5-9B | 98.30% (865/880) | 52.51% (157/299) | 97.76% | 68.37% |

9B реже добавляет неподтверждённые утверждения. По полноте однозначного
победителя нет: micro выше у 4B, macro — у 9B. Micro взвешивает длинные
источники с большим количеством фактов сильнее; macro уравнивает объявления.
Это предварительные модельные оценки, не доказательство статистического превосходства.

Gemini `gemini-3.5-flash-lite` дал 10/50 ответов; 40 запросов получили HTTP 429.
Отдельный ответ сервера подтвердил исчерпанную дневную free-tier квоту
500 запросов на проект/модель. На пересечении всех трёх моделей с определёнными
метриками осталось **7 входов**, только категории 102–104:

| Модель | Подтверждённость micro | Сохранение деталей micro |
| --- | ---: | ---: |
| Qwen3.5-4B | 96.38% (133/138) | 62.07% (18/29) |
| Qwen3.5-9B | 97.94% (95/97) | 65.52% (19/29) |
| Gemini 3.5 Flash-Lite | 97.73% (86/88) | 75.86% (22/29) |

Семь смещённых квотой входов недостаточны для общего рейтинга Gemini против Qwen.
Исходный Google-судья тоже упёрся в квоту; Structured API ответил 401.
Итоговые эталоны и оценки получены реальными вызовами `omp.eval.completion`,
затем replay прошёл строгую проверку схем и цитат. Точный model ID канала
не раскрывается — в результатах указан alias `default`, не придуманное имя.

Сводка с хешами, счётчиками и ограничениями:
[`comparison-results.json`](comparison-results.json).
Полные входы, черновики, утверждения, цитаты, ошибки и runtime:
`out/draft-model-comparison-v2/`.
Парный отчёт Qwen: `qwen-comparison.json` / `.md`;
первоначальное пересечение трёх моделей: `initial-comparison.json` / `.md`.
Настоящие completion IDs и ответы оценщика — `out/draft-judge-cache/`.
Время чтения replay не выдаётся за время модели.

Оба локальных сервера после проверки остановлены. Веса и изолированный
рантайм сохранены; основной `config.json`, `.env` и классификатор не менялись.

## Дополнение: Gemma 3 12B IT

Проверены те же 50 входов, неизменный промпт и замороженные исходные факты.
Использованы text-only веса `mlx-community/gemma-3-text-12b-it-4bit`,
ревизия `83eda451975103fff6f11e97bf75cd0f1c61af2c`.
Параметры совпадают с Qwen: 4 bit, temperature 0.2, seed 43, max_tokens 2048.
Ответы Qwen и Gemini не перегенерировались.

Gemma вернула **50 настоящих ответов**, каждый — JSON в Markdown-обёртке.
Строгий генератор отклонил **50/50**: его парсер и статусы не исправлялись.
Поэтому проверка интеграционного формата отделена от двух метрик содержания.

Явный режим `--semantic-content` одинаков для всех моделей:

* корректный ответ конвейера используется как раньше;
* у ошибочного ответа допускается только единственная внешняя Markdown-обёртка
  `json`/без языка, внутри которой находится объект исходной схемы `title`/`text`;
* пояснения снаружи, несколько объектов, лишние поля и пустой текст не допускаются;
* текст не переписывается, `generation_status`/`generation_error` сохраняются.
  Успех анализа содержания не означает успех генератора.

```bash
# Без --labels сравниваются все четыре модели.
uv run python src/draft_generation/benchmarks/sample_llm/compare.py --stage evaluate --semantic-content --judge-provider recorded --judge-responses-dir out/draft-judge-cache --output-dir out/draft-model-comparison-v2
```

Для Gemma 50 текстов доступны для оценки; 48 ответов оценщика прошли проверку,
два отклонены из-за неточных цитат. С учётом восьми пустых эталонов общее
пересечение трёх локальных моделей — **40 входов**:

| Модель | Подтверждённость micro | Сохранение деталей micro |
| --- | ---: | ---: |
| Qwen3.5-4B | 96.19% (909/945) | 56.46% (166/294) |
| Qwen3.5-9B | 98.26% (847/862) | 51.70% (152/294) |
| Gemma 3 12B IT | 98.58% (209/212) | 23.13% (68/294) |

На этой выборке Gemma немного выше по доле подтверждённых утверждений,
но сохраняет заметно меньше деталей. Это не повод менять Qwen-9B на Gemma:
малая разница по первой метрике не доказывает превосходства, а полнота ниже.
Без обработки формата Gemma также не является готовой заменой текущего генератора.

Общее пересечение с частично доступным Gemini — только **7 входов**:

| Модель | Подтверждённость micro | Сохранение деталей micro |
| --- | ---: | ---: |
| Qwen3.5-4B | 96.38% (133/138) | 62.07% (18/29) |
| Qwen3.5-9B | 97.94% (95/97) | 65.52% (19/29) |
| Gemma 3 12B IT | 100.00% (24/24) | 27.59% (8/29) |
| Gemini 3.5 Flash-Lite | 97.73% (86/88) | 75.86% (22/29) |

На семи входах нет оснований для общего рейтинга всех четырёх моделей.
Это оценки модельного судьи, не ручной эталон; прежние ограничения сохраняются.

Файлы в `out/draft-model-comparison-v2/`:

* `generation-gemma3-12b.json`: исходные ответы и все 50 ошибок строгого формата;
* `comparison.json` / `.md`: строгий режим, все четыре модели, без скрытия ошибок;
* `semantic-evaluation-<label>.json`: две метрики содержания с исходным статусом генерации;
* `local-content-comparison.json` / `.md`: одинаковые 40 входов для трёх локальных моделей;
* `semantic-comparison.json` / `.md`: все четыре модели, одинаковые 7 входов.

Сервер Gemma работал с `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`,
после прогона остановлен. По разрешению пользователя удалены только скачанные
веса Qwen-9B для освобождения места; его 50 ответов и все оценки сохранены.
Веса Qwen-4B, Gemma и изолированный runtime оставлены. Основной конфиг не переключён.

## Дополнительные метрики и ручное сравнение

Он содержит все 50 исходников и реальные доступные ответы четырёх моделей,

сырой ответ, включая Markdown, можно раскрыть. Недоступные ответы Gemini
помечены HTTP 429. Автооценки видны сразу; их и названия моделей можно скрыть
для ручного сравнения. Есть фильтр по категории и пять быстрых примеров —
первый вход каждой категории, выбранный до дополнительных оценок.
HTML самодостаточен и работает без сети. GitHub показывает HTML как исходный код:
скачайте файл и откройте его в браузере.

Первые две метрики вынесены в отдельную таблицу: **подтверждённость фактов**
и **сохранение полезных деталей**, в процентах с числителями и знаменателями.
Переключатель группы моделей меняет обе таблицы, но их выборки различаются:
для первых двух метрик N=40 у локальных моделей и N=7 у всех четырёх;
для дополнительных критериев — N=50 и N=10 соответственно.
Пустые эталоны и ошибки проверки цитат не превращаются в нули.

Добавлены три независимых критерия по шкале 0–4:

* **Релевантность категории:** тематический фокус, без переноса соседних услуг.
* **Читаемость:** ясность, грамотность и структура, без награды за многословие.
* **Самостоятельность:** понятно ли объявление без исходника. Общий, но понятный
  текст может быть самостоятельным; полезные детали измеряются отдельно.

Судья видит только готовый текст, цель и определения категорий из официального
справочника, без исходника и названия модели. Это не повторная проверка
фактологичности. Идентичные тексты одной категории используют одну оценку:
для 160 доступных текстов оценены 159 уникальных слепых состояний.
Оценщик: `openai-codex/gpt-6-astra`, 159/159 успешно. Полные ответы, распределения
и происхождение сохранены в `review-data.json` (поле `quality_judgments`);
рабочий кэш — `out/draft-model-comparison-v2/review-judgments.json`.
Это не ручной эталон.
Новые генерации не выполнялись.

### Воспроизведение опубликованного HTML

Исходные тексты, реальные ответы, замороженные факты, результаты первых проверок,
дополнительные оценки и сводные таблицы включены в [`review-data.json`](review-data.json).
Для пересборки опубликованного HTML не нужны API, веса моделей или папка `out`:

```bash
python3 src/draft_generation/benchmarks/sample_llm/render_review.py
```

Для пересборки данных из локальных кэшей эксперимента:

```bash
uv run python src/draft_generation/benchmarks/sample_llm/review.py --stage prepare
# review-requests.json фиксирует состояния и вопросы для реального judge_batch.
# Нужен сохранённый out/draft-model-comparison-v2/review-judgments.json.
uv run python src/draft_generation/benchmarks/sample_llm/review.py --stage assemble
python3 src/draft_generation/benchmarks/sample_llm/render_review.py
```

`prepare` не вызывает LLM. Новые состояния при необходимости оцениваются через
`judge_batch(states, questions, concurrency=16, retries=0)` в канале omp;
`review-judgments.json` содержит хеш identity запроса, metadata, answers и failed.
`assemble` проверяет соответствие входам и критериям, не заменяет пропуски нулями
и не выполняет новых генераций. Обычный Python-скрипт не притворяется модельным
каналом: отсутствие файла оценок — явная ошибка.

Сводка в репозитории: [`review-results.json`](review-results.json).
Полные данные: [`review-data.json`](review-data.json); автономный просмотр:
[`review.html`](review.html). Рабочие `extended-report.json` и `extended-report.md`
остаются в `out/draft-model-comparison-v2`.
Сами ответы и тексты в просмотре не исправлялись.
