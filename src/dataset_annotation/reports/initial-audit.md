## Что проверяем и почему

Проверены все 10 000 строк train и 208 строк test, а также постановка,
справочник категорий, критерии оценки и README исходных файлов.
Это аудит данных, а не оценка классификатора. Обучение, подбор промптов
и запросы к внешним моделям не выполнялись. Исходные данные не изменены.

Все строки проверены программно. Смысловая проверка сделана выборочно
по кандидатам, повторяющимся шаблонам и конфликтам; это НЕ ручная
переразметка всех 10 208 объявлений и НЕ оценка процента ошибочных меток.

```json
{
  "train": "docs/innoglobalhack_avito/public-train-annotated.jsonl",

  "near_duplicates": {

    "max_features": 100000,
```

Запуск из корня:

```sh

PYTHONPATH=src uv run python -m dataset_annotation.render_dataset_audit
PYTHONPATH=src uv run python -m dataset_annotation.render_train_audit
```

Полные описания, ссылки на строки, хеши файлов, группы повторов,
лексические кандидаты и близкие пары сохраняются в
`src/dataset_annotation/work/dataset-audit.json`.
Индексы в общих массивах кандидатов и групп — нулевые индексы `records`.
В `train.exact_duplicates` и `test.exact_duplicates` индексы локальны
соответствующей части. Поле `row` у записи — номер строки с единицы.
Для parquet это позиция записи после чтения в исходном порядке.

Лексические кандидаты — только повод прочитать контекст. Например,
«штукатурка не нужна» и объявление заказчика не доказывают пропуск метки.
Сходство шаблонов также не означает ошибку: разные списки услуг
закономерно должны иметь разные метки.

Особенно явные примеры:

- **41 / 161:** один и тот же текст предлагает штукатурку по маякам,
  поклейку обоев, укладку керамогранита, замену проводки и разводку труб.
  Пустые метки строки 41 противоречат явному перечню работ.
- **16 / 30:** «Штукатурка, шпаклевка… Покраска, поклейка обоев…
  разводка электрики и сантехники». Строка 30 имеет `[]`, строка 16 —
  `[102,104,105,106]`.
- **44 / 117:** «Штукатурные и шпаклевочные работы под покраску или обои».
  В строке 117 потеряна 106.
- **67 / 107:** реклама текстильных шумоизоляционных стен.
  «Аккуратные стыки, углы, розетки и выключатели» описывает качество
  отделки, но не предлагает электромонтаж. В строке 107 стоит 105,
  в остальных четырёх копиях `[]`.

При одинаковом исходном mcId детерминированное решение не сможет
полностью совпасть с этими метками: как минимум 22 строки должны иметь
несовпадение всего набора. Это комбинаторный факт, не измерение micro-F1.
В test отсутствует поле исходного mcId. Если он различался при разметке,
то без него сравнение невоспроизводимо; при этом различие `[]` и пяти
категорий нельзя объяснить одним только исключением исходной категории.

### Корректный контекст «только под ключ»

По заранее выписанным узким формулировкам:

```text
только под ключ
только дом целиком
исключительно по формату
не берём в работу отдельные
```

найдено 48 строк train, 23 дословно уникальных описания.
Все 48 имеют пустые метки. Проверенные выше примеры включают явные услуги.
Это наблюдаемая связь, но не доказательство внутреннего алгоритма разметки.

**Уточнение пользователя:** если исполнитель явно принимает только квартиру/дом
целиком и не берётся за отдельные работы, перечисленные этапы не являются
дополнительными отдельно принимаемыми услугами. Пустые метки у четырёх
разобранных выше примеров корректны; моя прежняя претензия отозвана.
Само выражение «под ключ» без ограничения на отдельные заказы не доказывает
такой запрет. Шаблонные кандидаты всё равно требуют проверки контекста.
Исходные метки и документы постановки не менялись.

### Почему нельзя автоматически исправлять всё по словам

Строка **90**, item_id **2511719500936**, имеет `[]`, хотя содержит
«выравнивание штукатуркой», «поклейка обоев», «вывод 1 новой розетки».
Это корректный отрицательный пример: начало «Требуется выполнить…»,
конец «Жду ваших предложений…». Объявление разместил заказчик,
а не исполнитель, предлагающий перечисленные услуги.

Характеристики также нельзя безусловно обрезать: у строк 810, 1686, 2409,
2489, 3578, 5532, 7609 общий рекламный текст дословно совпадает, но хвост
содержит разные конкретные услуги и обоснованно меняет метки.

## 3. Ограничения покрытия задачи

- Все исходные категории train приняты равными 101; нет материала
  для полноценной проверки распознавания 101 и других исходных mcId.
- В test есть только title, description, categories — исходный mcId не записан.
- `title` присутствует в обоих файлах, но отсутствует во входном контракте.
  Нельзя восполнять отсутствующие в description услуги из заголовка.
- Train содержит обрывки и шум: строка 9439 — «Р», строка 9672 — «С»,
  строка 101 — «7777». Их пустые метки не обязательно ошибочны,
  но они не проверяют понимание услуг.
- README прямо предупреждает об автоматической, не полностью ручной разметке.
  Согласие с ней не равно доказанной смысловой корректности.
- После этого аудита test уже просмотрен: его нельзя использовать
  для подбора правил и одновременно называть нетронутым финальным holdout.

## Выводы

Главный подтверждённый дефект — разные метки у одинаковых test-описаний.
Явное ограничение только комплексным заказом учтено как корректное основание
для пустого набора, а не ошибка. Остальные смысловые вопросы —
различение штукатурки и шпаклёвки/каркасного выравнивания, политика
по SEO-хвостам и характеристикам.

Исходники и метки не исправлялись. Для дальнейшей оценки нужны
согласованные правила, ручной разбор спорных групп и разбиение
с удержанием дубликатов и близких шаблонов в одной части.
