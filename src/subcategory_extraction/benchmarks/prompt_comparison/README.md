# Сравнение модулей и промптов

Сервис: subcategory_extraction.

## Что проверяем

TF-IDF и оба текущих промпта Google Decision выполняют настоящий `run()` на
одних и тех же 32 объявлениях. Источник — официальный train, только группы
validation из разбиения бенчмарка [TF-IDF](../tfidf_quality/README.md).
Выборка: `random.Random(43).sample`, без повторения нормализованного описания.
SHA-256 исходника: `b7118d68086624fbeab43839f22a635d4e325e4ee339f22d4aa0ad3c2e986615`.
Ожидаемые метки берутся из `found_microcategories`; исходная категория 101.
Метрика: micro-F1 по 101–106; исходная категория в ответе даёт FP.

Модель Google: `gemini-decision-1`; порог 0.5.
Критерий лучшего промпта — максимальный micro-F1 на этих одинаковых validation-входах.
Получен **guided**. Рабочие промпты и `config.json` автоматически не меняются.

## Запуск

```bash
uv run python src/subcategory_extraction/benchmarks/tfidf_quality/run.py
uv run python src/subcategory_extraction/benchmarks/prompt_comparison/run.py
```

Первый запуск создаёт локальные веса. Второй выполняет **64 настоящих run() Google с обращением к API**,
по 32 на промпт, и 32 локальных вызова. Число HTTP-попыток может быть больше
при повторах. Нужны настройки Google в `.env`.
`--size` меняет размер выборки, `--report` — путь отчёта.
[Полный отчёт](results.json) содержит входы, эталоны, ответы, хеши промптов
и время каждого вызова. Кэш не подставляется.

## Ограничения

32 входа и автоматические метки дают предварительное сравнение.
Это validation, не финальный test. Новые ответы не сравниваются с прежним
смешанным CSV или внешним SplitShift: у них другие данные и целевые метки.
TF-IDF отличается от guided на очень малое значение F1 — статистическая
значимость этой разницы не проверялась.
