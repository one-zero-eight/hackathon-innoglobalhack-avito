# CPU-инференс и стоимость внешних LLM

Сервис: `subcategory_extraction`, общий учёт также для `draft_generation`.
Ветка: `leo/feature/cpu-costs`, база `ecd71de`.

## Что реально сделано

Существующий `semantic_encoder` — **дообученный cointegrated/rubert-tiny2**, не
TinyBERT и не замороженные embeddings. Все веса encoder и multilabel-голова уже
обучены на 4821 отфильтрованном официальном train-тексте. Нового обучения,
validation, поиска порога или подбора по public-test в этом запуске нет.

Инференс принудительно выполнен на **CPU**, без MPS/GPU. Официальная оценка —
все 208 строк, 139 уникальных входов; одинаковый вход вычисляется один раз,
но все эталоны участвуют в micro-F1. Вход/выход `drafts` не менялся.

[Машиночитаемый отчёт с usage, предсказаниями и хешами кода](results/cpu-costs.json).
[Архитектура и исходное обучение](semantic-encoder.md).

Apple M4 Pro, macOS arm64; последовательный batch=1 документ, до трёх окон
512 токенов на документ, существующие FP32-веса, без квантования.

| Public-test строк | 208 |

| Загрузка pipeline, включая импорты/веса | 1.196 с |
| Инференс всех уникальных входов | 0.697 с |

Время инференса не включает загрузку pipeline; первая инференс-операция не
исключалась. Это измерение на данном CPU, не обещание такой же скорости на
любом ноутбуке/сервере. Команда общего запуска пяти вариантов заняла 3.70 с;
это не время одного encoder и не время нового API-инференса.

На CPU и прежнем MPS **совпали все 208 предсказанных наборов**. Предсказания
остальных четырёх базовых вариантов также побитово совпали по наборам меток
с опубликованными результатами `ecd71de`.

классификационную таблицу: при включении внешнего генератора его вызовы платные
или имеют неизвестную цену даже с полностью локальным классификатором.

## Учёт расходов

Общий `main.LLMCostLedger` подключён к Jev, StructuredLLMClient, Google Decisions
и Gemini-генератору. Записывается **каждая HTTP-попытка**, в том числе повтор
после временной ошибки. Usage учитывается сразу после чтения ответа, до
валидации категории/текста: некорректный ответ модели не становится бесплатным.
Кэш Jev/structured и исторический Google replay учитываются отдельно.

Журнал хранит только endpoint/model, явные token counters, локальный/provider
cache, ошибку и тарифное основание. Заголовки, ключи, промпты и объявления в
журнал стоимости не попадают.

- `fresh_estimated_usd`: оценка новых внешних вызовов этого запуска.
- `cold_estimated_usd`: гипотетическая цена тех же зарегистрированных ответов
  без **локального** кэша, с теми же токенами/тарифами. Это не новый замер API.
- `known_fresh_estimated_subtotal_usd`: только известная часть оценки; неизвестные
  события не исчезают, полный итог при них остаётся `null`.
- `api_attempts`, `local_cache_hits`, `failed_attempts` и счётчики неизвестных цен.
- `events`: фактические счётчики и использованные ставки, источник/дата тарифа.

Локальный кэш даёт fresh=0, но не cold=0. Если тариф/usage отсутствует, модель
или endpoint не совпали, цена — **null**, а не ноль. Неудачная HTTP-попытка без
счётчиков также имеет неизвестный биллинг: не утверждаем, что она бесплатная.
У Google GenerateContent к выходным токенам прибавляются `thoughtsTokenCount`;
OpenAI-compatible `completion_tokens` уже включает reasoning. `total_tokens`
не подменяет отдельные input/output, если их нет.

Provider cache — другое: `cached_tokens`/`cachedContentTokenCount` вычитаются
из обычного input и считаются по отдельной ставке. Если таких токенов больше
нуля, но cached-ставка не задана, итог неизвестен. Денежная арифметика — Decimal.

Только flat token charges, **оценка, не invoice**: налоги, комиссии, free tier,
context-dependent tiers, хранение cache и локальные вычисления не включены.
Оценку следует сверять с биллингом провайдера.

## Где отчёт появляется

```bash
uv run python src/main.py --input data/input.json --output out/output.json
```

Помимо неизменённого `output.json`, создаётся `out/output.json.costs.json`.
Флаг `--cost-report` меняет путь. Стоимость сохраняется и при исключении после
вызовов API. `run.py` включает общий журнал обоих шагов в `report.costs`; при
ошибке сохраняет `<report>.costs.json` без фиктивной итоговой метрики.
Общий `compare_methods` добавляет `costs` каждому завершённому/упавшему методу.
При программном использовании доступен `client.costs.summary()`; для нескольких
клиентов/потоков общий журнал задаётся через `track_llm_costs(ledger)` в потоке
вызова. Сам runner делает это для каждого worker.

## Тарифы: не подменять провайдера

`LLM_PRICING_FILE` задаёт путь к JSON вида `{"currency":"USD","rates":[]}`.
Пустой/неуказанный каталог означает **неизвестные тарифы**, не бесплатный API.
Каждый элемент `rates` содержит:

| Поле | Смысл |
| --- | --- |
| `endpoint`, `model` | Точные строки из реального клиента/журнала |
| `input_per_million`, `output_per_million` | Неотрицательные конечные USD-ставки, можно decimal-строками |
| `cached_input_per_million` | Отдельная ставка provider cache, если применяется |
| `source` | Проверенный источник ставки для данного провайдера/аккаунта |
| `checked_at` | Дата проверки тарифа |

Дубликаты endpoint/model и NaN/Infinity/отрицательные цены отклоняются.
Ставки разных endpoint не наследуются, даже если model ID совпадает.
У генератора endpoint — полный `.../models/<model>:generateContent`.

Публичная [страница BestAPI](https://bestapi.fugue.pro/models) сообщает единицы
«за 1M токенов», но в доступном HTML и отдельном JS-браузере не отдала чисел.
Действующий тариф данного BestAPI-аккаунта не подтверждён; ранее предоставленный
ключ уже отклонялся с 401, повторных проверок ключа и платных вызовов не делали.

Есть **отдельный ориентир, не цена BestAPI**:
[TypeSafe напрямую публикует](https://help.typesafe.ai/articles/5187202169-how-much-does-jev-cost)
Jev input **$0.042/1M**, output **$0**, без request/minimum fees. По фактическому
usage 139 сохранённых ответов Jev — 390390 input, 13761 output — при этом
**гипотетическом прямом тарифе** вышло бы **$0.01639638**, или около
**$0.11796 за 1000 уникальных объявлений** с тем же средним размером.
Это не списание за текущий запуск, не тариф посредника и не цена полного
решения с генерацией. Ставка автоматически в BestAPI-каталог не перенесена.

Google replay содержит 208 исходных ответов, а Jev/гибрид — 139 уникальных
входов. Журнал отражает именно эти события; абсолютные cold-суммы нельзя
сравнивать как одинаковую нагрузку без нормализации.

## Воспроизведение и проверки

Сначала подготовить локальные артефакты по [основному отчёту](classifier-methods.md).
Затем:

```bash
SEMANTIC_ENCODER_DEVICE=cpu PYTHONPATH=src uv run python -m subcategory_extraction.benchmarks.compare_methods --methods semantic_encoder --workers 1 --report out/encoder-cpu.json

# Требует настоящего Jev-кэша либо рабочего API-ключа; Google по умолчанию — replay.
SEMANTIC_ENCODER_DEVICE=cpu PYTHONPATH=src uv run python -m subcategory_extraction.benchmarks.compare_methods --methods google_decision jev tfidf jev_tfidf semantic_encoder --workers 2 --report out/methods-cpu-costs.json
```

Для измеренного запуска ключи были намеренно пустыми в окружении: все внешние
ответы взяты из настоящего кэша/replay, фактических API-попыток **0**.
Отдельный throwaway-прогон арифметики проверил точность Decimal, различие двух
видов cache, reasoning tokens, несовпадающие endpoint/model, неизвестные usage,
частичный итог после ошибки, отсутствующую cached-ставку и недопустимые цены.
Он не вызывал модели и не участвовал в расчёте F1.
Реальные `main.py` и `run.py` запущены на официальном входе, для которого
сохранённый Jev не предлагает дополнительных категорий: оба сохранили расходы,
`drafts` остался пустым, генератор не вызывался. Новых платных upstream-ответов
для проверки invoice не получено.

## Решение

CPU для текущего encoder уже достаточно быстр; замена на TinyBERT сама по себе
не доказывает улучшение качества. Приоритет для собственной модели — уменьшить
143 FP и шум автоматических train-меток, а не только уменьшить число параметров.
Дистилляция сильного учителя на официальном train — возможный следующий
эксперимент с отдельным заранее посчитанным бюджетом, **здесь не запускалась**.
Default остаётся Jev: локальный encoder пока не превзошёл его. Для автономного
CPU-режима доступен `subcategory_extraction: "semantic_encoder"`; внешний
`sample_llm` всё равно требует отдельного бюджета или самостоятельной замены.

## Проверка ошибок CLI

Оба реальных CLI дополнительно запущены с изолированным пустым Jev-кэшем и
пустым ключом. Оба корректно завершились ошибкой до сетевого запроса, сохранили
cost sidecar с нулём API-попыток и не создали фиктивные drafts/итоговый F1.
Это проверка сохранения отчёта при сбое, не повторная проверка отклонённого ключа.
