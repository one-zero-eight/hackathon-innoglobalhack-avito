# Jev: ближайшие положительный и отрицательный примеры

Сервис: `subcategory_extraction`; модуль: `jev_retrieval`.
Дата: 2026-11-14.

## Вход и интерфейс

```json
{
  "description": "Предлагаем штукатурку стен по маякам и поклейку обоев. Электрику не выполняем.",
  "mcId": 101
}
```

`SubcategoryExtractionPipeline()` создаётся без аргументов;
`run(PipelineInput) -> list[int]` возвращает дополнительные категории без
исходного `mcId`. Передаваемый модели `state` — только полное исходное
`description`, никогда не конкатенация объявления с примерами.

## Зафиксированный метод

Модель по умолчанию — нативная `jev-1.13.0`, через существующий `JevClient`
и SystemOne BestAPI, не генерация вероятностей текстовой моделью.
Для каждой из пяти категорий, отличных от исходной, задаётся независимый
вопрос Noul. Начальная инструкция — существующий guided-промпт Jev.
Положительный ответ включается при `p >= 0.5` в зафиксированном сравнении.

Справочник — `out/hybrid-training.jsonl`: подготовленная из официального
InnoGlobalHack train выборка после исключения компонентов точных и близких
пересечений с публичным test. Исключение использует тексты, не test-метки;
сам retrieval не читает test или его метки. Подготовку справочника выполняет
общий сценарий, этот модуль не создаёт и не заменяет обучающие данные.

Формат строки справочника:

```json
{
  "description": "Выполняем штукатурку стен по маякам.",
  "found_microcategories": [{"mcId": 102}]
}
```

Это иллюстрация формата, не утверждение о наличии такой строки в train.
Метки читаются только из `found_microcategories[].mcId`; целые ID должны
принадлежать общей таблице `MICROCATEGORIES` и отличаться от исходной 101.
Официальный train имеет исходную категорию 101; необязательное поле `mcId`
при его наличии также должно быть целым 101. Пустые дополнительные метки
допустимы. Некорректные строки отклоняются, включая длинные строки, которые
затем не попадут в индекс.

В индекс включаются **полные** описания длиной не более 1800 символов.
Обрезки нет: нельзя переносить положительную метку на фрагмент, из которого
исчезла подтверждающая услуга. TF-IDF: `analyzer=char_wb`, символьные
n-граммы `(3, 5)`, `min_df=2`, `max_features=40000`, L2-нормировка,
остальные параметры — стандартные `TfidfVectorizer`.

Для одного объявления выполняется один `transform` и один расчёт сходства
со всем индексом. При L2-нормировке `s(q, d) = q · d` — косинусное сходство.
После исключения всех normalized-exact совпадений с запросом для категории
`c` выбираются `argmax s(q,d)` среди `c ∈ labels(d)` и среди `c ∉ labels(d)`.
При равенстве сходства выигрывает меньший исходный номер строки JSONL.
Нормализация совпадений совпадает с общим аудитом: Unicode NFKC, casefold,
`ё → е`, свёртка пробельных последовательностей.

Два полных описания с `category_mc_id` и булевой `offered` передаются в
инструкции как явно ограниченные JSON-данные, не команды и не исходное
объявление. Решение по-прежнему принимается только по исходному `state`.
Если после исключения совпадений нет обеих меток, категория получает только
исходное guided-правило. В частности, для 101 в этом train нет положительных
примеров: отрицательная подсказка вместо пары не создаётся.

Порог, вариант индекса и правила выбора фиксируются до оценки. Validation,
holdout, подбор по test и корректировки вероятностей после API отсутствуют.

## Настройки и кэши

- `JEV_REFERENCE_DATASET`: путь к JSONL, по умолчанию корневой `out/hybrid-training.jsonl`.
- `JEV_REFERENCE_MAX_CHARS`: положительное целое, по умолчанию `1800`.
- Общие параметры нативного клиента: `BESTAPI_API_KEY`, `JEV_MODEL`
  (по умолчанию `jev-1.13.0`), `JEV_ENDPOINT`, `JEV_TIMEOUT`, `JEV_CACHE_DIR`.
- Как у базового Jev, `JEV_PROMPT_PATH` меняет guided-промпт,
  `JEV_THRESHOLD` — порог. Для фиксированного сравнения используется штатный
  guided и `JEV_THRESHOLD=0.5`, без подбора этих параметров.

Индекс создаётся в конструкторе, не при импорте. `functools.lru_cache`
переиспользует его по абсолютному пути, `mtime_ns` и лимиту длины. Ошибки
чтения, неверные метки и отсутствие подходящих текстов не скрываются.
Нативный клиент отдельно кэширует только проверенные реальные ответы API
по endpoint и полному payload: изменение примеров меняет ключ кэша.

Для общего отчёта доступны `reference_metadata` (`path`, SHA-256 **всего**
JSONL, `rows` — число проиндексированных полных описаний, `max_chars`,
`index_spec`), `last_references` (номера выбранных строк и сходства по
категориям), `client`, `threshold`, `probabilities(inp, categories=None)`.
Отсутствие категории в `last_references` означает отсутствие пары, не нулевую
вероятность. `client.last_cache_hit` и `client.last_usage` относятся к
последнему реальному вызову клиента.

## Запуск и оценка

Из корня репозитория, после подготовки общего справочника и `.env`:

```bash
PYTHONPATH=src JEV_THRESHOLD=0.5 uv run python -m subcategory_extraction.benchmarks.compare_methods --methods jev_retrieval
```

Оценка — все 208 официальных строк, включая противоречивые дубликаты, без
разбиения или удаления неудобных примеров. Общий runner рассчитывает
sklearn micro-F1 через `run.calculate_metrics` и `60 × micro-F1`, сохраняет
фактический model ID, затраты и происхождение данных. Этот документ
фиксирует метод, а не измеренный результат; результаты и сравнение методов
публикуются в [общем отчёте](classifier-methods.md), машиночитаемые данные —
в `results/classifier-methods.json`.
