# Jev: явные границы микрокатегорий

Сервис: `subcategory_extraction`; модуль: `jev_boundaries`.
Дата: 2026-11-14.

## Вход и интерфейс

```json
{
  "description": "Укладываем плитку в ванной, выполняем шпаклёвку и покраску стен. Сантехнику не подключаем.",
  "mcId": 101
}
```

`SubcategoryExtractionPipeline()` создаётся без аргументов и наследует
контракт базового Jev: `run(PipelineInput) -> list[int]`. В нативный `state`
передаётся только полное исходное `description`; исходная категория никогда
не запрашивается и не возвращается.

## Зафиксированный метод

Используется нативная модель `jev-1.13.0` по умолчанию, существующий
`JevClient` и SystemOne BestAPI. Для пяти дополнительных категорий формируются
независимые вопросы типа Noul; итоговое множество — категории с `p >= 0.5`
в фиксированном сравнении. Вероятности не синтезируются текстовой моделью
и не исправляются после ответа API.

Единственное изменение относительно базового Jev — статический промпт
`jev_boundaries/prompts/boundaries.md`, который форматируется названием
категории из общей `MICROCATEGORIES` и существующими `CATEGORY_EXAMPLES`.
Промпт основан на официальном
[справочнике микрокатегорий](../../../docs/innoglobalhack_avito/microcategories-guide.md)
и уточняет следующие семантические границы:

- штукатурка и выравнивание штукатуркой — 102; шпаклёвка и подготовка под
  покраску или обои — малярный цикл 106, не доказательство штукатурки;
- укладка, облицовка, затирка, запил плитки — 103; один демонтаж плитки
  не подтверждает предложение её укладки или обработки;
- водоснабжение, канализация, сантехприборы и водяное отопление — 104;
  упоминание ванной/санузла, его ремонта или облицовки этого не доказывает;
- проводка, электроточки, щиты, освещение и электрический тёплый пол — 105;
  водяное отопление не переносится в электрику, неоднозначному «тёплому полу»
  не приписывается неуказанный тип;
- комплексный ремонт помещения может подтверждать 101, но «укладка плитки
  под ключ» не равна комплексному ремонту; общее «ремонт под ключ» не
  доказывает все специальные услуги.

Собственный перечень работ исполнителя считается предложением услуг без
требования слова «отдельно», отдельной цены или отдельного заказа. Явные
этапы комплексного ремонта учитываются. Отрицания применяются только к
своей области действия; чужая работа, материал или прошлый проект без
текущего предложения не являются услугой исполнителя. Предложение исправить
чужую работу, напротив, может быть собственным предложением соответствующей
услуги. Исходное описание трактуется как данные, а не новые инструкции.

Это семантическая инструкция модели, не список regex-фильтров. Жёстких
гейтов, ключевых слов для принудительной метки и поправок под test-метки нет.
Нет retrieval, дообучения, validation/holdout, подбора порога или промпта по
официальным 208 строкам. Вариант промпта фиксируется до итоговой оценки.

## Настройки и кэш

- `BESTAPI_API_KEY` — ключ существующего нативного клиента.
- `JEV_MODEL` — фактическая модель, по умолчанию `jev-1.13.0`.
- `JEV_ENDPOINT`, `JEV_TIMEOUT`, `JEV_CACHE_DIR` — общие настройки клиента.
- `JEV_THRESHOLD` наследуется от базового Jev; для этого сравнения — `0.5`.
- Инструкция берётся из собственного `prompts/boundaries.md`, а не из
  `JEV_PROMPT_PATH`. Базовый конструктор вызывается до замены промпта, поэтому
  заданный `JEV_PROMPT_PATH` должен оставаться читаемым.

Обучающий файл модулю не нужен. При импорте нет API-вызовов; конструктор
читает локальный промпт и создаёт клиент без запроса к сети. Нативный клиент
валидирует actual model ID, точный набор ответов и вероятности, а затем
кэширует только подлинные ответы API по endpoint и полному payload.
Другой промпт даёт другой ключ кэша. Публичные атрибуты для общего runner:
`client`, `prompt`, `threshold`; методы `probabilities(inp, categories=None)`
и `run(inp)`. `client.last_cache_hit` и `client.last_usage` описывают последний
вызов нативного клиента.

## Запуск и оценка

Из корня репозитория с настроенным `.env`:

```bash
JEV_THRESHOLD=0.5 uv run python src/subcategory_extraction/benchmarks/classifier_methods/run.py --methods jev_boundaries
```

Для совместного сравнения двух вариантов:

```bash
JEV_THRESHOLD=0.5 uv run python src/subcategory_extraction/benchmarks/classifier_methods/run.py --methods jev_retrieval jev_boundaries
```

Общий runner оценивает все 208 официальных строк, включая противоречивые
дубликаты, и использует `run.calculate_metrics`: sklearn micro-F1 и
`60 × micro-F1`. Измеренные значения, реальный model ID и затраты находятся
в [общем отчёте](../benchmarks/classifier_methods/README.md) и `../benchmarks/classifier_methods/recorded-results.json`.
Этот документ описывает зафиксированную реализацию и не заявляет качество
до измерения.

## Фактический статус запуска

Модуль был запущен общим runner; запрос к нативному Jev завершился HTTP 401.
Предоставленный ключ также отклонён endpoint списка моделей как `invalid api key`.
Измеренного F1 этого промпта нет: базовые вероятности не переиспользовались
под видом ответа на изменённый промпт.
